# BRIEF.md: бэкенд MVP для сервиса ИИ-анализа российских компаний

Это справочный материал по проекту. Правила работы, запреты и порядок фаз смотри в `AGENTS.md`.

## 1. Контекст проекта

Разрабатываем веб-сервис для поиска, проверки и последующего ИИ-анализа российских юридических лиц и индивидуальных предпринимателей.

Пользователь должен иметь возможность найти компанию по ИНН, ОГРН/ОГРНИП или названию, получить структурированные сведения из разных источников, изучить финансовые показатели, налоговую информацию и другие доступные данные.

В будущем сервис получит полноценного ИИ-агента, который сам будет обращаться к инструментам поиска, сопоставлять данные, анализировать организации, выявлять потенциальные риски и формировать отчёты с подтверждающими источниками.

**Сейчас разрабатываем исключительно инфраструктуру данных и бэкенд.** Нужна основа, которая позволит позже реализовать ИИ-агента без существенной переработки бизнес-логики.

### Стек

- Backend: Go + Gin.
- Database: PostgreSQL.
- Frontend: Next.js (сейчас не реализуется).

Остальные технологии, библиотеки и архитектурные решения выбираешь и обосновываешь сам. Redis, очереди, микросервисы, векторные базы и прочее добавляй только при конкретной технической необходимости.

### Принцип работы

Ты отвечаешь за архитектурное проектирование и технические решения. Структуру папок, таблицы, названия моделей, организацию сервисов и библиотеки никто заранее не навязывает. Нужно самостоятельно изучить информацию, сравнить альтернативы и предложить наиболее подходящую архитектуру MVP.

Работа делится на Фазу A (исследование и предложение) и Фазу B (реализация). Подробности и гейт между ними описаны в `AGENTS.md`.

## 2. Источники данных

Подход гибридный:

- Собственная база данных, пополняемая бесплатными открытыми выгрузками ФНС.
- DaData API для регистрационных данных и поиска компаний.
- Возможность подключения дополнительных источников в будущем.

Предпочтение отдаётся официальным машиночитаемым выгрузкам, а не парсингу HTML.

### 2.1. Федеральная налоговая служба

| Источник | Назначение | Приоритет |
|---|---|---|
| Реестр МСП | Сведения об организациях и ИП, относящихся к МСП | P0 |
| Доходы и расходы организаций | Финансовые показатели | P0 |
| Среднесписочная численность | Количество работников | P1 |
| Уплаченные налоги и сборы | Налоговые показатели | P1 |
| Налоговая задолженность | Сведения о задолженностях на отчётную дату | P1 |
| Специальные налоговые режимы | Информация о применяемых режимах | P1 |

Основные ресурсы:

- https://www.nalog.gov.ru/opendata/
- https://www.nalog.gov.ru/opendata/7707329152-rsmp/
- https://www.nalog.gov.ru/opendata/7707329152-revexp/
- https://egrul.nalog.ru/
- https://bo.nalog.gov.ru/

Эти ссылки не считаются готовыми API или гарантированно действующими URL для прямой загрузки.

Перед проектированием импорта выясни:

- Какие наборы действительно доступны бесплатно.
- Где находятся актуальные файлы.
- В каком формате они публикуются.
- Какие XML/XSD используются.
- Каковы реальные размеры архивов.
- Как представлены юрлица и ИП.
- Какие идентификаторы присутствуют.
- Какие поля доступны.
- Как часто обновляется каждый набор.
- Публикуется полный снимок или набор изменений.
- Есть ли предыдущие исторические выгрузки.
- Какие ограничения существуют на хранение и коммерческое использование.

**Важно:**

- Бесплатные наборы ФНС не эквивалентны полной базе ЕГРЮЛ/ЕГРИП. Не проектируй систему так, будто они содержат все российские организации.
- Не предполагай, что показатели для юрлиц в таком же виде доступны для ИП.

Если найдёшь дополнительные бесплатные официальные источники, полезные для MVP, изучи их и предложи подключение с обоснованием.

### 2.2. DaData

Документация: https://dadata.ru/api/

Назначение:

- Поиск организации или ИП по ИНН.
- Поиск по ОГРН/ОГРНИП.
- Поиск по названию.
- Получение доступных регистрационных реквизитов.
- Дополнение локальной базы данными, которых нет в открытых наборах ФНС.

Изучи методы `findById/party` и `suggest/party`.

Исследуй:

- Форматы запросов и ответов.
- Доступные поля.
- Различия между тарифами.
- Лимиты бесплатного тарифа.
- Обработку ошибок и превышения квот.
- Условия хранения и кэширования полученных данных.
- Разрешение на использование данных в коммерческом публичном сервисе.

Право на API-запрос не означает автоматически право на постоянное хранение ответа или его перепродажу. Предложи стратегию, которая минимизирует зависимость от DaData и не нарушает условия использования.

### 2.3. Другие источники (только дизайн расширяемости)

В перспективе система должна поддерживать интеграции с:

- ГИР БО.
- КАД Арбитр.
- Федресурсом.
- ФССП.
- ЕИС Закупки.
- Другими официальными и коммерческими поставщиками.

## 3. Архитектурные требования

### 3.1. Общая архитектура

Нужна наиболее подходящая архитектура для небольшой, но потенциально масштабируемой системы. Предпочтение простому, поддерживаемому решению без преждевременного усложнения.

Концептуально разделить:

- HTTP API.
- Бизнес-логику.
- Получение данных из внешних источников.
- Импорт массовых выгрузок.
- Хранение информации.
- Обновление данных.
- Подготовку данных для будущих ИИ-инструментов.

Это разделение ответственности, а не предписание создать именно такое число пакетов или слоёв. Структуру директорий выбираешь сам и обосновываешь, чем она лучше альтернатив для данного MVP.

### 3.2. PostgreSQL

Схему проектируешь сам. Она должна позволять хранить:

- Организации.
- Индивидуальных предпринимателей.
- Регистрационные сведения.
- Финансовую информацию по отчётным периодам.
- Налоговые показатели.
- Сведения МСП.
- Происхождение данных.
- Даты актуальности сведений.
- Метаданные загруженных наборов.
- Историю выполнения импортов.

Решить самостоятельно:

- Нужна ли единая модель для ООО/АО/ИП.
- Какие таблицы необходимы.
- Какие связи использовать.
- Как устроить нормализацию.
- Где оправдан JSONB.
- Какие индексы создать.
- Как обрабатывать противоречивые данные.
- Как хранить историю изменений.
- Как проводить миграции.

Учитывай:

- ИНН юрлица: 10 цифр. ИНН физлица и ИП: 12 цифр.
- ОГРН юрлица: 13 цифр. ОГРНИП: 15 цифр.
- Идентификаторы хранятся как строки.
- Отсутствие показателя не равно нулевому значению.
- Финансовые показатели относятся к определённым отчётным периодам.
- Не все сведения применимы одновременно к ООО и ИП.
- При совпадении ИНН разные идентификаторы и регистрационные записи требуют корректной обработки.

Модель обязана сохранять происхождение показателей. Это особенно важно для будущего ИИ-анализа.

### 3.3. Импорт данных ФНС

Нужна надёжная система массовой загрузки. Она должна учитывать:

- Загрузку больших архивов.
- Потоковый разбор XML.
- Различные XSD.
- Возможные изменения схем.
- Ограниченное потребление оперативной памяти.
- Пакетную запись в PostgreSQL.
- Обновление существующих записей.
- Идемпотентность.
- Повторные попытки после временных ошибок.
- Отслеживание прогресса.
- Защиту от повреждённых файлов.
- Восстановление после прерывания.
- Избежание параллельного импорта одного набора.
- Возможность ручного запуска.
- Автоматическое обновление по расписанию.
- Сохранность предыдущих корректных данных при неудачном обновлении.

Оцени затраты на хранение и обработку по реальным размерам выгрузок, если удастся их определить.

Не предполагай, что все наборы ФНС имеют одинаковый формат или стратегию обновления.

### 3.4. Агрегация данных

Пример сценария (можно предложить лучше):

1. Пользователь запрашивает ИНН.
2. Система ищет сведения в PostgreSQL.
3. При необходимости обращается к DaData.
4. Объединяет доступные данные.
5. Возвращает структурированный результат.
6. Указывает источник и дату актуальности каждого существенного показателя.

Нужно корректно различать состояния:

- Сведения найдены.
- Сведения не опубликованы.
- Показатель неприменим.
- Сведения устарели.
- Внешний источник временно недоступен.
- Компания не найдена.

При недоступности DaData локальные сведения должны оставаться доступными.

## 4. REST API

API будут использовать: Next.js frontend, собственный ИИ-агент, потенциально внешние интеграции.

Возможности:

**Поиск:** по ИНН, по ОГРН/ОГРНИП, по названию, с пагинацией.

**Карточка компании:** идентификаторы, название, регистрационный статус, дата регистрации, основной вид деятельности, доступные публичные реквизиты, дополнительные данные из подключённых источников.

**Финансы:** доходы и расходы, история доступных отчётных периодов, другие финансовые показатели, если источники их дают.

**Налоги:** уплаченные налоги, доступные сведения о задолженности, отчётные периоды.

**Другие данные:** принадлежность к МСП, численность сотрудников, применяемые налоговые режимы, источники и даты актуальности.

Маршруты, форматы JSON и структуру ответов предлагаешь сам.

API должен иметь:

- Версионирование.
- Валидацию входных данных.
- Единообразные ошибки.
- Документацию OpenAPI.
- Разумное ограничение запросов.
- Корректную обработку недоступности внешних источников.

Не нужен отдельный endpoint на каждое поле, если это ухудшает архитектуру. Найди баланс между компактностью API и возможностью получать конкретные категории данных без избыточной загрузки.

## 5. Подготовка к будущему ИИ-агенту

ИИ-агента сейчас не реализуем. Бэкенд должен быть спроектирован так, чтобы будущий агент использовал существующие операции как инструменты.

Предварительные названия инструментов (можно предложить лучше):

- `search_companies`
- `get_company_profile`
- `get_company_financials`
- `get_company_taxes`
- `get_company_sources`

Будущий сценарий. Пользователь: «Проверь компанию по ИНН и скажи, стоит ли заключать с ней договор». Агент:

1. Определяет, какие сведения нужны.
2. Вызывает подходящие инструменты.
3. Получает структурированные данные от Go-сервиса.
4. Анализирует сведения.
5. Формирует аргументированный ответ.
6. Приводит источники и даты актуальности.

Нужно заранее продумать, как инструменты будут получать данные, но не создавать их реализации.

**MCP или обычный Tool Calling?** Исследуй, что лучше для собственного агента. Предполагается, что внутренний агент вызывает операции Go-бэкенда напрямую через типизированные инструменты. MCP может понадобиться позже для внешних клиентов. Не внедряй MCP без необходимости.

**Будущий маршрутизатор LLM.** Позже планируется роутер между ИИ-провайдерами, включая бесплатные тарифы. Он будет учитывать: доступные модели, их возможности и ограничения, квоты, стоимость, скорость, ошибки, переключение между провайдерами. Сейчас роутер, управление API-ключами и LLM-интеграции не разрабатываем. Важно лишь не создавать архитектурных ограничений, которые затруднят их подключение.

## 7. Предварительная последовательность этапов

Это черновик. Его можно скорректировать с обоснованием, он не является утверждённым планом.

**Этап 1. Foundation:** инициализация Go-проекта, Gin, подключение PostgreSQL, миграции, конфигурация, логирование, Docker Compose, базовые проверки работоспособности.

**Этап 2. Data Infrastructure:** загрузчик архивов, XML-парсер, пакетная запись, метаданные источников, учёт импортов, повторное выполнение и обновление данных.

**Этап 3. FNS Integration:** реестр МСП, доходы и расходы, среднесписочная численность, уплаченные налоги, налоговая задолженность, специальные налоговые режимы.

**Этап 4. DaData Integration:** HTTP-клиент, поиск по ИНН и по названию, нормализация данных, обработка лимитов, стратегия кэширования с учётом лицензии, объединение данных с PostgreSQL.

**Этап 5. REST API:** поиск организаций и ИП, карточка, финансовые сведения, налоговые сведения, источники, валидация, документация OpenAPI.

**Этап 6. Production Readiness:** автообновление данных, мониторинг импортов, обработка сбоев, тестирование, оптимизация запросов, документация развёртывания, проверка конфигурации безопасности.

**Этап 7. AI Readiness:** описание контрактов будущих инструментов, проверка пригодности API для ИИ-вызовов, документирование способов получения подтверждений и источников, архитектурные рекомендации для следующей фазы. ИИ в рамках текущего этапа не реализуется.

## 8. Ожидаемый результат MVP

Система должна:

1. Находить российские организации и ИП по ИНН.
2. Поддерживать поиск по названию и ОГРН/ОГРНИП.
3. Хранить доступные открытые сведения ФНС локально.
4. Предоставлять доступные финансовые и налоговые показатели.
5. Дополнять информацию через DaData.
6. Сохранять источники и даты актуальности.
7. Автоматически обновлять поддерживаемые наборы данных.
8. Не терять корректные сведения при сбое обновления.
9. Предоставлять документированный REST API.
10. Быть готовой к подключению собственного ИИ-агента.

Если отдельные показатели недоступны по объективным причинам, это должно явно отражаться в API.
