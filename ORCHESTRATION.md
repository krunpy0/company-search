# Правила работы над фронтендом

## Требования к реализации

- Экраны с референсами делай максимально точно по ним. Остальные проектируй
  по DESIGN.md, сохраняя визуальную целостность.
- Используй Impeccable; при конфликте приоритет у DESIGN.md.
- Учитывай существующую архитектуру и возможности бэкенда.
- Адаптивность (вьюпорты из DESIGN.md), состояния загрузки, ошибок, пустые состояния.

## Бэкенд

- Если не хватает эндпоинта, создай его в рамках существующей архитектуры
  (удаление аккаунта, смена пароля, настройки и т.п.).
- Существующие контракты не меняй, только добавляй новое.
- Для новых эндпоинтов пиши тесты в стиле существующих, перечисли их в отчёте.
- Деньги (оплата, подписки, биллинг, баланс): не трогай, пиши в BLOCKERS.md.

## Организация

- Главный агент: оркестратор. Сам почти не пишет код, делегирует.
- Исполнители (код, бэкенд, тесты): GPT 6.2Sol, medium.
- Проверяющий (интерфейс через Chromium): Gemini 4 Hydrogen.
  Исполнители свою работу не проверяют.
- PROGRESS.md: что сделано, дизайн-решения, готовые общие компоненты,
  что осталось. Обновляй после каждого этапа, читай при возобновлении.
- После каждого крупного этапа делай git commit.
- Сначала один исполнитель делает фундамент (токены, базовые компоненты,
  layout, API-клиент, роутинг). Потом экраны раздаются исполнителям, до 3 параллельно.
- У каждого исполнителя своя зона файлов (директория его экрана). Нужен новый
  общий компонент или правка общих файлов: он возвращает запрос оркестратору.
- Исполнителю передавай: DESIGN.md, актуальный PROGRESS.md, референсы,
  список общих компонентов, ожидаемое поведение, критерии готовности.
  Он возвращает короткую сводку (что сделано, какие файлы, что не вышло).

## Проверка

После каждого крупного этапа запускай проверяющего с Chromium:
соответствие референсам и DESIGN.md, пользовательские сценарии, адаптивность
на вьюпортах из DESIGN.md (скриншоты на каждом), дефекты и ошибки консоли.

Перед этим сам сформулируй ожидаемое поведение: визуальный результат,
сценарии, критерии корректности. Передай их проверяющему с референсами и DESIGN.md.

Промпт проверяющему пиши нейтрально: объективно сопоставь результат с
ожидаемым, без поиска ошибок ради ошибок и улучшений ради улучшений, но и без
подгонки под «всё хорошо». Реализация может быть полностью корректной.
Он возвращает: что совпало, что нет (с наблюдениями и скриншотами),
ошибки консоли. Без советов «на будущее».
Расхождения передавай исполнителю, затем перепроверяй только затронутые экраны.

## Правила отметки и завершения

- Пункт TODO отмечай только после реализации и проверки.
- Не останавливайся после этапов и не ограничивайся планом.
  Некритичные решения принимай сам.
