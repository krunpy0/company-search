# Фронтенд ScanINN

## Исходное состояние

В `61dc12a` реализованы 16.1–16.4. Сценарии и объём предыдущей проверки записаны в `TODO-FRONTEND.md`. Для поиска и карточки ещё нужна сквозная проверка на Go API с тестовыми данными.

В работе общий слой для 16.5–16.9. После него идут чат, история, настройки и системные экраны. Галочки в TODO обновляются после проверки соответствующих сценариев.

## Дизайн и общие компоненты

Сохраняем композицию лендинга и обоих состояний чата из `design/design-reference/landing`, Onest, тёмные поверхности и красный акцент из `design/design-reference/DESIGN.md`. Новые рабочие экраны используют те же токены. Контрольные ширины в CSS px: 320, 375, 390, 768, 1024, 1440 и 1920.

Существуют глобальные токены, стили кнопок и полей, каркас авторизованной области, общий слой сессии и сгенерированные из OpenAPI типы. Точные точки подключения уточняются на этапе фундамента.

## План завершающей реализации

- Общий слой: доступные диалоги на нативном `<dialog>`, действующие токены и клиент OpenAPI.
- Рабочая область: выбор регистрации и восстановление отправки, поиск и управление диалогами, экспорт из сохранённых данных.
- Настройки и системные экраны: профиль, изменение учётных данных, управление историей, помощь и обратная связь. Для операций со штатными данными добавляем только новые маршруты и тесты, сохраняя действующие контракты.
- Приёмка: отдельная PostgreSQL с фикстурой репозитория, локальный подменный LLM, Go API и Chromium. Обращения к DaData и платным моделям на стенде отключены.

## Общий слой и стенд

- Общий `WorkspaceDialog` использует нативный модальный режим, токены DESIGN.md и прокрутку внутри панели. Подключён к входу в настройки. ESLint и сборка прошли, независимая проверка Chromium запущена.
- Локальный стенд запущен на `127.0.0.1:48162`, Go API на `127.0.0.1:48160`. Используются отдельная PostgreSQL с фикстурой `stage10.sql` и подменная модель на loopback. Проверены готовность API, вход, чтение карточки и ответ чата с тремя записями источника.
- Исходный набор Go-тестов прошёл. Для проверок API авторизации и чата использовались отдельные БД и роль `company_api`.
